# 双语译文链接丢失：定位与改造方案

2026-11-03 · v0.8.0 问题定位；已在 v0.9.0 实施为[通用行内标签映射](inline-structure.md)

## v0.8.0 已确认的原因

段落原文的链接仍存在，新增的双语译文没有生成链接节点。问题发生在本地渲染阶段。

| 模式 | 实际做法 | 链接结果 |
| --- | --- | --- |
| 双语普通段落 | 将片段译文拼成字符串，创建新 span，通过 textContent 写入 | 只有链接文案，没有 a 和 href |
| 仅译文 | 将片段译文写入原 Text.data，原 a 元素保持不动 | 地址、target 及原节点上的点击事件保留 |
| 短导航等紧凑控件 | 在原控件内部追加文字 | 可借助外层原 a 保持可点击，不能据此判定普通段落也正常 |

v0.8.0 代码定位：content/reader.js 的 render 在 178–180 行将整段文字传给 insertion；translationElement 的第 70 行执行 element.textContent = text。仅译文分支在 184–185 行直接更新 slot.node.data。收集阶段已经保留 slot.node，模型结果也已经有按 ID 对齐的 record.values，因此链接与译文的对应关系仍可利用。

这同样解释了行内强调、代码等结构为什么在新增的整段译文中可能退化为普通文字。CSS 配色只能改变观感，不能为纯文字补回真正的链接节点。

## 复现证据

使用 v0.8.0 交付 ZIP 的原始文件，在隔离浏览器中加载一个段落，包含 URL 文案链接和“the guide”这类普通文案链接。本地固定响应服务完整返回片段，并故意倒序，验证现有 ID 对齐仍有效。一次真实 HTTP 请求即可复现。

| 检查 | 实测 |
| --- | --- |
| 双语原文的可点击链接 | 2 个，原节点和地址保留 |
| 双语新增译文的可点击链接 | 0 个，译文 HTML 完全是纯文字 |
| 仅译文模式的链接 | 2 个，原节点身份、地址和点击监听仍正常 |
| 切回双语后 | 再次为 0 个链接，新增模型请求为 0 |

因此，片段翻译和切换复用都正常，缺口是双语段落没有还原行内结构。现有整页回归验证了原文链接和仅译文节点保留，没有断言双语新增译文本身包含可点击链接。

复现命令：

```sh
node scripts/e2e.mjs tests/bilingual_links_diagnostic.py
```

该断言在 v0.8.0 因双语译文缺少链接而失败，属于已捕捉的缺陷；v0.9.0 同一复现已通过。历史机器记录：verification/bilingual-link-analysis-0.8.0.json；修复后记录：verification/bilingual-link-analysis-0.9.0.json。

## 推荐方案：本地结构骨架与片段译文组合

1. **保留来源结构。** 继续利用 slot.node 和稳定片段 ID，在本地记录各片段所属的原链接及允许保留的行内标签。地址和 DOM 引用留在本地，不交给模型生成。
2. **按片段生成译文节点。** 用 record.values 填充对应 Text 节点，组合为 DocumentFragment；链接片段使用真实 a，连续属于同一个原链接的片段合成同一个链接。可以同时保留 strong、em、code、br 等受控结构。
3. **目标地址取自原网页。** 读取并检查原链接当前有效的 href，保留必要的 target、rel、title 等属性。原 URL 文案保持原样，普通链接文案可以翻译；不从翻译后的可见文字猜地址。
4. **保持阅读设计。** 译文继续按块追加、字号减 2px、无底色和侧线；链接沿用译文颜色，增加下划线及键盘焦点。独立导航仍沿用紧凑渲染，避免在已有 a 内再创建嵌套 a。
5. **复用现有缓存。** ShiyiPageMap 已保存逐片段 values、源节点路径及链接目标指纹。结构匹配的旧缓存可以结合当前 DOM 直接重绘，不需要为修复显示额外调用模型。源结构或链接已变更时，仍遵守原有严格匹配，不使用陈旧目标。

普通有真实 href 的链接优先保持浏览器原生点击、组合键、中键和右键菜单行为。克隆节点不会复制 addEventListener 或属性方式绑定的点击处理，也可能制造重复 ID，因此需要受控地创建节点，不能直接克隆整个段落；依赖自定义点击／路由处理的链接要单独验证和适配。[Mozilla DOM 文档](https://developer.mozilla.org/en-US/docs/Web/API/Node/cloneNode)

内容脚本和页面脚本的 JavaScript 环境相互隔离，因此不能假定能够读取并复用页面私有路由回调；对无法可靠复现行为的脚本控件，应保留原控件操作入口。[Chrome 内容脚本文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

## 不选其他补法的原因

| 方法 | 局限 |
| --- | --- |
| 把看起来像 URL 的译文用正则转链接 | 无法恢复“指南”“点击这里”等文字背后的地址，也可能把标点或错误地址一起识别进去 |
| 要求模型输出 HTML | 把结构和地址的正确性依赖于模型，并改变现有纯文本安全边界；增加输出内容，仍不能保证事件和路由保留 |
| 整段 cloneNode(true) 后替换文字 | 会复制不需要的属性、重复 ID 和控件；程序化事件监听不会随节点复制 |

## 实施与验收范围

主要调整 reader.js 的非紧凑双语渲染，必要时提取受控行内节点生成器，并在 content.css 补链接的下划线和焦点样式。无需改变翻译模型接口、批次大小、并发数或本地词库格式。只在确实需要处理缺少片段映射的旧记录时，使用该块的原文操作入口或单独重译该块，不清空词库或要求整页重译。

验收须新增“双语译文本身可点击”的断言，并覆盖：

- URL 文案、普通链接文案、相对路径、绝对地址、页面锚点、一个链接内多个强调片段，以及同文案不同地址。
- 普通点击、新标签打开、组合键／中键、键盘及右键复制链接地址；对脚本路由另行验证。
- 双语／仅译文切换和刷新缓存后仍可点击，复用已有结果时新增请求为 0。
- 恢复原文后，原节点、原事件、原 HTML 保持一致；不产生嵌套链接、重复 ID 或重复标记闪烁。
- 页面改变或移除链接时不留下错误目标；模型文字始终按文字处理，不解析模型生成的 HTML 或事件属性。

本方案已在 v0.9.0 扩展为通用行内标签映射并实现。复现测试已转绿，双语译文中的两个链接均可点击；嵌套标签、代码、font、原位升级与旧缓存重建另有 21 项专项验证。实现范围与事件边界见[通用行内标签映射](inline-structure.md)。
